1. **읽기 기록의 값 형식**: 모델이 `reading` 값을 `{"count": 3}`처럼 객체로 적는 일이 많다(프롬프트 예시는 `7`). 분류기는 이를 "결과 해석 불일치(전사 오류)"로 보지만 뒤에서 쓰이지 않으면 무해로 처리한다. 프롬프트에 "값만 적어라"를 넣을지, 분류기가 객체를 벗겨 비교할지 정해야 한다(아직 하지 않음, 분류 규칙 조정은 dev로).
2. **해석 어휘**: 해석이 항상 가장 이른 턴이라 어휘를 정확히 못 맞추면 뒤의 다른 오류보다 먼저 첫 이탈이 된다. 특히 `answer_type`(int/float) 구분은 모델이 자주 틀리지만 답에는 영향이 없다. 해석 단계의 판정 필드를 줄일지 검토 필요 (`docs/interpretation_cases.md`).
3. **조건 2의 실패율이 정확히 10.0%**(경계). 프롬프트를 더 조정하지는 않았다(dev만 보고 계속 조정하면 과적합 위험).
4. **오탐 주입 규칙의 의미**: 이제 오탐 주입은 "실제 탐지기의 오탐 빈도"를 흉내 내지 않는다(누락 주입과 같은 규모). 논문 한계에 적을 것.
5. **남은 위험**: 재시작하면 결정성이 없으므로 본 실행 도중 서버가 죽으면 이어 하기 이후 기록은 이전 기록과 같은 시드여도 다른 궤적일 수 있다. 동결 뒤 실행기에 서버 재시작 감지를 넣을지 검토.
