# HRSID 실제 파일 구조 확인 결과 (M0, SPEC §4.1)

2026-09-29, `data/hrsid/HRSID_JPG/`의 파일을 직접 열어 센 값만 적었다. 확인하지 못한 것은 "확인 불가"로 표시한다.
로더: `src/sarqa/data/hrsid.py`.

## 1. 파일 구성

```
data/hrsid/HRSID_JPG/
├── JPEGImages/                 5,604개 .jpg (주석에 없는 파일 0개, 주석에 있는데 없는 파일 0개)
├── annotations/
│   ├── train2017.json          3,642 영상 / 11,047 상자
│   ├── test2017.json           1,962 영상 /  5,922 상자
│   └── train_test2017.json     5,604 영상 / 16,951 상자
└── inshore_offshore/
    ├── inshore.json            1,031 영상 /  8,206 상자
    └── offshore.json           4,573 영상 /  8,745 상자
```

- `HRSID_JPG.zip`(같은 폴더의 상위)의 목록에도 위 `.jpg`와 `.json` 5개 외 다른 파일(README, 메타데이터 등)은 없다.
- 형식은 모두 COCO 형식: 최상위 키 `info, licenses, images, type, annotations, categories`. 범주는 `ship` 하나(id 1).
- 영상 항목 키: `id, file_name, width, height, license, url, date_captured`. 이 중 `url`과 `date_captured`는 전 영상에서 `None`, `license`는 전부 0. 영상별 그 밖의 필드는 없다.
- 상자 항목 키: `id, image_id, category_id, bbox, segmentation, area, iscrowd`. `bbox`는 COCO `[x, y, w, h]`, 픽셀. 전 상자 `iscrowd=0`, `category_id=1`, `segmentation` 비어 있지 않음. 영상 밖으로 나간 상자 0개, 너비·높이가 0 이하인 상자 0개.
- 영상 id는 각 파일 안에서 0부터 연속이다. **파일 사이의 id는 서로 다르므로 `file_name`으로 대응시켜야 한다** (예: `train_test2017.json`의 id 0은 `P0001_0_800_10190_10990.jpg`, `train2017.json`의 id 0은 `P0001_0_800_7200_8000.jpg`).

## 2. 영상 수, 상자 수, 크기

- 영상 5,604장. 파일 이름 중복 없음. JSON의 `width/height`와 PIL로 연 실제 크기 모두 **800×800 전량**. 모드는 **RGB 전량**(3채널; PIL `mode` 확인).
- 상자 16,951개. 긴 변(px)의 분위수: 최소 3, 25% 21, 중앙 42, 75% 57, 최대 800.
- 영상당 선박 수: 0척 0장, 1척 2,720장, **2~15척 2,786장**(문항 대상 후보, §5.3), 16척 이상 98장, 최대 163척.
- 2~15척 영상의 연안/외해 구성: 연안 767장, 외해 2,019장 (아래 §4 태그 기준).

## 3. 공식 train/test 목록

- `train2017.json` 3,642장, `test2017.json` 1,962장. 서로 겹치는 영상 없음, 합치면 `train_test2017.json`의 5,604장과 정확히 같은 집합.
- 두 파일에 포함된 상자 합(11,047 + 5,922 = 16,969)이 `train_test2017.json`(16,951)보다 **18개 많다**. 영상 26장(공식 train 18장, test 8장)에서 상자 수가 서로 다르다 (공식 쪽이 22장에서 1개 많고 4장에서 1개 적음). 예: `P0001_2400_3200_2400_3200.jpg`는 `train_test2017.json` 1개, 공식 파일 2개. 어느 쪽이 맞는지는 파일만으로 판단할 수 없다.
- `inshore.json`·`offshore.json`의 상자는 `train_test2017.json`과 **전 영상에서 동일**하다 (상자 합 8,206 + 8,745 = 16,951, 영상별 상자 목록 불일치 0장).
- → 이 저장소에서 라벨 상자의 기준으로 `train_test2017.json`을 쓰는 것이 연안/외해 파일과 일관된다. 26장 불일치는 그대로 두고 여기에 기록한다 (사용자 확인 요청 항목).

## 4. 연안/외해 태그

- 태그 필드는 없고, **파일 소속**(`inshore.json` / `offshore.json`)이 태그다.
- 두 파일의 영상 집합은 서로 겹치지 않고, 합집합이 5,604장 전체와 같다. **1,031 + 4,573 = 5,604 확인.**
- 따라서 공식 train 3,642장(연안 662 / 외해 2,980)과 공식 test 1,962장(연안 369 / 외해 1,593) **모두 태그가 있다.** 일부 영상에만 있는 경우가 아니다.
- 장면(§5의 P0001~P0136) 단위로 보면 태그가 영상마다 다르다: 연안만 8개 장면, 외해만 31개 장면, **연안·외해가 섞인 장면 97개.** (장면 하나가 통째로 연안/외해인 것이 아니라 조각 단위 태그다.)

## 5. 원본 장면 ID·절단 좌표

- 5,495장의 이름이 `P<장면 4자리>_<x1>_<x2>_<y1>_<y2>.jpg` 규칙이다. 장면 ID는 `P0001`~`P0136`, 136개 전부 존재하고 빠진 번호가 없다. 좌표 4개는 모두 800 차이(800×800 절단)이며 `x1 x2 y1 y2` 순서로 보인다(예: `P0001_0_800_7200_8000` → x 0~800, y 7200~8000).
- 나머지 **109장은 `P0137_<번호>.jpg`(번호 1~109)** 로, 절단 좌표가 없고 장면 ID `P0137`을 가진다. SPEC이 말한 "136개 원본 장면"에 들어가지 않는 **137번째 접두어**다. 이 109장의 실제 원본 관계는 파일에서 확인할 수 없다. 공식 분할: train 70장 / test 39장. 태그: 연안 17 / 외해 92. 상자 146개.
- 장면별 영상 수(P0001~P0136): 최소 4, 중앙 42, 최대 96. **모든 136개 장면에서 같은 장면의 조각끼리 공간적으로 겹치는 쌍이 있다** (x·y 오프셋 차이가 모두 800 미만인 쌍 존재).
- **공식 분할은 장면 단위가 아니다**: P0001~P0136 중 135개 장면이 공식 train과 test 양쪽에 걸쳐 있다 (한쪽에만 있는 장면은 `P0119` 하나). → SPEC §4.2대로 공식 분할을 쓰지 않고 장면 묶음으로 다시 나눠야 하는 근거가 확인됐다.
- 이 규칙은 **파일 이름에서만** 얻은 것이다. 주석에는 장면 ID·절단 좌표 필드가 따로 없다.

## 6. 해상도(m/px), 센서, 촬영 지역 — **파일에 없음**

- 영상별 해상도(m/px)를 주는 필드는 **어느 JSON에도 없다** (§1의 키 목록이 전부). `info`의 `description/url/version/contributor`도 `None`.
- 센서, 촬영 지역(항구), 촬영 시기, 편파 등을 알려 주는 필드·파일도 없다.
- 이름의 `P0001`~`P0136`이 어떤 센서·해상도·지역에 대응하는지는 이 파일들만으로는 **확인 불가**다. (SPEC이 말하는 세 해상도 0.5/1/3 m는 SPEC의 서술이며, 이 데이터 폴더에서 확인한 사실이 아니다.)
- 영향: SPEC §4.1/§5.3/§15에 따라 `get_metadata`에서 해상도를 빼고 거리·길이 문항을 px 단위로 바꿀지, §4.2 층화에서 센서·해상도 층을 쓸지가 걸린 결정이다 → **§16-1, 사용자 결정 대기.**

## 10. 장면 묶음 (`splits/scenes.json`, `sarqa data scenes`)

- **방법**: (1) 파일 이름의 장면 접두어 `P<번호>`로 묶는다 (SPEC §4.2 (2)의 "영상 이름 규칙", 주석에는 장면 ID·절단 좌표 필드가 없으므로 (1)은 해당 없음). (2) 그 위에서, **JPEG 바이트가 완전히 같은 영상을 공유하는 장면들은 하나의 묶음으로 합친다.** 유사도(dHash)는 묶음 근거로 쓰지 않았다.
- **바이트 동일 영상**: 서로 다른 장면 ID인데 파일 바이트(md5)가 같은 영상이 3쌍(6장) 있다. 추정이 아니라 파일 사실이다. 이 중 2쌍은 첫 분할 시도에서 서로 다른 분할(test와 det_train)에 들어갔었다.

| 영상 쌍 | 합친 묶음 |
|---|---|
| `P0105_0_800_8400_9200.jpg` = `P0106_0_800_8400_9200.jpg` | G0105 ← G0106 |
| `P0115_4200_5000_9000_9800.jpg` = `P0116_4200_5000_9000_9800.jpg` | G0115 ← G0116 |
| `P0133_600_1400_1800_2600.jpg` = `P0135_600_1400_1800_2600.jpg` | G0133 ← G0135 |

  같은 영상이라도 상자 수가 다른 경우가 있다 (예: P0115 타일 26개 vs P0116 타일 24개). 같은 영상에 다른 라벨이 붙어 있다는 뜻이므로 데이터 한계로 적어 둔다.
- **묶음 근거별 영상 비율** (5,604장):

| 근거 | 영상 수 | 비율 |
|---|---|---|
| 파일 이름의 장면 ID + 절단 좌표 (`P<id>_x1_x2_y1_y2.jpg`) | 5,416 | 96.65% |
| 파일 이름의 장면 ID만 (`P0137_<n>.jpg`, 좌표 없음) | 109 | 1.95% |
| 바이트 동일 영상으로 다른 장면에서 합쳐진 묶음의 영상 (G0106, G0116, G0135의 79장) | 79 | 1.41% |
| 유사도 | 0 | 0% |

- 묶음 **134개**: 원본 장면 136개 중 3쌍이 합쳐져 133개 + `G0137`(원본 관계를 알 수 없는 109장, `origin_unknown=true`).
- 영상과 묶음 ID의 대응, 묶음별 영상 수·연안 영상 수·`merged_from`은 `splits/scenes.json`에 있다.
- **센서·해상도·지역 정보가 없다** (§6). 그래서 **같은 항구·지역을 다른 시기에 찍은 장면이 서로 다른 묶음으로 들어가 있는지는 알 수 없고**, 그런 장면이 있으면 분할 사이에서 지역 누수가 생길 수 있다. 검사할 방법이 없으므로 논문의 한계로 적는다 (SPEC §4.2 지역 누수).

## 11. 층화 분할 (`splits/splits.json`, `splits/splits_report.json`, `sarqa data splits`)

**방법** (SPEC §4.2 (4), 사용자 결정 2·3·4)
- 분할 단위는 §10의 묶음이다. `G0137`(`P0137_*`, 원본 불명)은 `det_train` 전용으로 고정하고 나머지 **133개 묶음**을 나눈다.
- 묶음 수 목표: 평가 25% → 33개(dev 30% → 10개, test 23개), `det_val` 10% → 13개, `det_train` 나머지 87개. 난수 시드로 고정한다.
- 층: **묶음의 영상 수(중앙값 43 이하/초과) × 묶음의 연안 영상 비율 구간**(0 / (0, 0.15] / (0.15, 0.40] / 0.40 초과) = 8개 층. 층 안에서 무작위 순서로 정렬하고 목표 개수대로 교차 배열한 카드 묶음에서 순서대로 나눠 주므로 각 층이 네 분할에 거의 비례해 들어간다.
- 시드는 0~999 중 **분할 간 영상 수 비율과 연안 영상 비율의 불균형이 가장 작은 값**(seed 25)을 골랐다. 질문·탐지 결과를 보지 않은 순수 기하 기준이며 test 결과와 무관하다.
- 해상도·센서·지역은 층화에 쓰지 못했다 (§6). 세 해상도가 test에 들어갔는지는 확인할 수 없다.

**결과**

| 분할 | 묶음 수 | 영상 수 (전체 대비) | 연안 영상 | 연안 비율 | 질문 후보 영상(2~15척, 26장 제외) |
|---|---|---|---|---|---|
| det_train | 88 (= 87 + `G0137`) | 3,722 (66.4%) | 679 | 18.24% | — |
| det_train (`G0137` 109장 제외) | 87 | 3,613 | 662 | 18.32% | — |
| det_val | 13 | 527 (9.4%) | 97 | 18.41% | — |
| dev | 10 | 393 (7.0%) | 71 | 18.07% | 186 (연안 59) |
| test | 23 | 962 (17.2%) | 184 | 19.13% | 467 (연안 136) |
| 평가 = dev + test | 33 | 1,355 (24.2%) | 255 | 18.82% | 653 |

- 평가(dev+test) 묶음이 **33개**이고 test는 **23개**다. SPEC이 예상한 약 34/24보다 하나씩 적다 (바이트 동일 영상으로 3쌍을 합쳤기 때문). 부트스트랩이 이 묶음 수로 돌아가므로 신뢰구간이 넓게 나오는 것은 설계상 예상된 결과다.
- 층 분포: test 23개는 8개 층 중 7개, dev 10개는 6개 층에 걸친다. test에 연안 영상이 없는 묶음이 5개, 전부 연안인 묶음이 1개다.
- 26장(§9): det_train 15, det_val 4, **test 7**, dev 0. test의 7장은 질문 후보에서 뺀다 (`question_eligible=false`). 검출기 학습·검증에는 쓴다.
- `question_eligible`은 dev/test 소속이면서 26장이 아닌 영상이다. 라벨 선박 2~15척 필터(§5.3)는 문항 생성(M3)에서 적용하며, 위 표의 후보 수는 이 조건까지 적용한 값이다.

**겹침 검사** (`overlap_check`, 통과)
- 모든 영상이 정확히 한 분할에 배정됨 (5,604장 = `scenes.json`과 같은 집합).
- 둘 이상의 분할에 걸친 묶음 0개, 분할 쌍마다 공유하는 묶음 0개 (dev∩test 0, det_train∩test 0 포함).
- 같은 묶음의 조각은 절단 좌표상 서로 겹치는데, 서로 다른 분할에 있는 겹치는 조각 쌍은 0개.
- 보조 dHash 검사(묶음 근거로 쓰지 않음, Hamming 거리 ≤ 4): 빈 바다 영상은 해시가 거의 0이라 서로 우연히 일치하므로 해시 1의 개수가 12~52개인 2,808장만 비교했다. 분할 간(서로 다른 묶음) 후보 쌍 9개가 나왔고, 축소 영상의 상관계수가 0.29~0.62이며 서로 다른 영상이다(같은 영상이면 1.0). 이 중 `P0137_*`와 엮인 쌍은 없다. 다만 절단 위치가 어긋난 재절단은 이 방법으로 찾을 수 없으므로 `G0137`의 원본 관계는 여전히 확인 불가다.
